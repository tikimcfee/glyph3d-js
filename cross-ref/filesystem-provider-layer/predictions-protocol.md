# Predictions: protocol

## About integration

I predict the integration agent focused heavily on where the `FileSystemRegistry` gets instantiated and threaded through — likely concluding it belongs in `IDEShell.js` as a top-level dependency injected into `GitHubRepoViewer`, with provider selection driven by URL parameters or a new UI element in `CommandBar` or `Drawer`. They probably identified that `GitHubRepoViewer._loadRepository()` and the `RepositoryAdapter` calls are the main surgery sites, where `repoAdapter.getFileContent(owner, repo, path, branch)` gets replaced with `fsRegistry.readFile(uri)`, and flagged the challenge of the viewer currently assuming GitHub-shaped data everywhere (owner/repo/branch as separate arguments rather than a single URI). They likely also addressed the relay server WebSocket changes — noting that the existing `WebSocketBridge` needs a JSON-RPC routing layer alongside existing command traffic, and that the `glyph3d-cli` Go binary needs new `fs/*` method handlers wired into its relay loop, probably recommending a handler registry pattern in Go rather than a giant switch statement.

## About grid-editing

I predict the grid-editing agent identified the core inversion problem: the buffer builder pipeline (`textToGlyphs` / `buildBuffers`) converts text lines into Float32Array instance attributes with per-glyph widths from the atlas, and editing requires mapping a 3D world-space pick coordinate (or a buffer slot index from `PickingSystem.resolve()`) back to a `{line, character}` text position. They likely concluded that `CodeGrid._lineSlotBase` (the Int32Array mapping line to buffer slot) is the essential lookup table for the line dimension, but character-within-line requires cumulative per-glyph width sums or a secondary index built during the same buffer pass. For cursor representation, they probably proposed either a dedicated glyph slot with a blinking highlight (reusing the highlight DataTexture with a timer) or a thin `THREE.Mesh` positioned using atlas metrics. They almost certainly flagged re-rendering after edits as the most performance-sensitive concern — noting that a single-character insert shifts all subsequent buffer slots, and recommending either a line-granular partial re-flush (rebuild only affected lines' buffer regions and use `addUpdateRange`) or the simpler but costlier full `loadFileAsync` re-render, with the line-granular approach deferred to a later optimization pass.
