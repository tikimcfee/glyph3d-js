# Predictions: integration

## About protocol

The protocol agent likely concluded that the provider interface should follow a JSON-RPC 2.0 wire format (or a close approximation) with `id`-correlated request/response pairs, `method` fields like `fs/list`, `fs/read`, `fs/write`, `fs/stat`, and a structured error object with numeric codes -- drawing heavily from LSP's transport model since the codebase already has LSP-style TextEdit references. They probably defined a URI scheme (`glyph://github/owner/repo/path` vs `glyph://local/path` vs `glyph://memory/path`) to unify resource identification across providers, and specified that notifications (file-changed, file-deleted) flow as server-initiated events without an `id` field. Their key concern was likely around the tension between keeping the protocol simple enough for the relay's current text-command model versus making it expressive enough for write operations, and they probably flagged that the existing WebSocket bridge lacks request/response correlation -- the same gap I identified -- and proposed either adding it or adopting a thin JSON-RPC framing layer.

## About grid-editing

The grid-editing agent almost certainly identified the core inversion problem: the buffer builder pipeline (`textToGlyphs` / `layoutText` / `buildBuffers`) is a one-way transformation from source text to Float32Array instance attributes, and there is no reverse mapping from a 3D glyph slot index back to a `(line, column)` text position -- meaning they need to build or extend `_lineSlotBase` and per-glyph metadata to support bidirectional mapping. They likely proposed a cursor model as a `{ line, col }` logical position that gets projected into 3D world coordinates using atlas metrics and CodeGrid's transform, with keyboard input captured by a new focus state on CodeGrid (probably extending TUIFocusManager or adding a parallel mechanism). Their biggest concern was probably re-rendering efficiency after edits: a single character insertion invalidates every subsequent glyph's buffer slot position on that line (and all following lines if a newline is inserted), so they likely proposed either a line-granular re-render (rebuild only the affected line's buffer region using `addUpdateRange`) or a full grid re-flush, and flagged that the worker pipeline would need to support partial/incremental buffer rebuilds rather than always rebuilding the entire file's buffer from scratch.
