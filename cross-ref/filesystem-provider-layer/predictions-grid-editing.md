# Predictions: grid-editing

## About protocol

The protocol agent likely settled on a JSON-RPC 2.0 wire format over the existing WebSocket relay, modeling the provider interface after LSP's TextDocumentContentProvider and FileSystemProvider with methods like `fs/readFile`, `fs/writeFile`, `fs/readDirectory`, and `fs/stat`, plus a `textDocument/didChange` notification for pushing edits upstream. They probably defined a URI scheme (`glyph://` or `provider://`) to distinguish between local file access, GitHub API access, and relay-proxied filesystem access, and flagged that TextEdit ranges must use raw character offsets (line, character) matching LSP semantics -- which aligns directly with my `slotToPos` storing `rawCol`. A key concern would be versioning/sequencing of edits to avoid lost-update races when the relay round-trip introduces latency, likely proposing monotonic version numbers on document snapshots and requiring the client to send the base version with each edit batch.

## About integration

The integration agent likely focused on how the provider abstraction slots into `GitHubRepoViewer.js` and `IDEShell.js`, probably proposing a `FileSystemProviderRegistry` that the app shell instantiates at startup and that `CodeGrid.loadTextAsync` calls through instead of directly fetching content via `fetch()` or the GitHub API. They would have identified the viewer's current `loadContent` / `fetchFileContent` path as the seam to intercept, and proposed a UI element in the CommandBar or a new drawer panel for selecting the active provider (local, GitHub, relay). A major concern would be the relay server extensions needed in `ws-relay.mjs` / `ws-relay.py` to proxy filesystem operations from the Go CLI or a local agent, and they likely concluded that the relay needs new message types routed to a filesystem handler rather than being purely a command passthrough -- essentially turning the relay into a bidirectional RPC bridge rather than a unidirectional command pipe.
