# Predictions from Infrastructure Agent

## About Commands Agent

Commands likely migrated all `resolveGrid(grids, arg)` call sites to `resolveGridByIdOrIndex(ctx, arg)` and rewired grid iteration to use `ctx.registry.findByType('grid')` or `ctx.getGrids()`. They probably rewrote `grid.list` to show registry IDs alongside indices, and `grid.remove` to accept string IDs. What they likely missed: the `scene.reset` command does reverse-order iteration over grids to avoid index-shift bugs during removal -- with registry-based removal this is unnecessary, but commands agent may have kept the reverse iteration pattern out of caution, adding dead complexity. They also likely did not define what `addGrid` returns -- some command handlers need the registry ID back from addGrid to include in their response, and if addGrid's return value is not specified, grid.create has to do a separate `registry.getIdByGrid()` call afterward.

## About Viewer Agent

Viewer likely replaced `this.grids = []` with a getter that derives from the registry, added cache invalidation on mutation, and migrated `createGridForFileAsync`, `clearGrids`, and `loadDiff` to use registry calls. They probably added a setter trap that throws on direct assignment to catch `this.grids = result.grids` regressions. What they likely missed: the `loadRepository` loop at line 886-888 does `scene.add(grid)` and `this.grids.push(grid)` -- if `createGridForFileAsync` already registers, the push is redundant, but removing it means `scene.add` is the only remaining statement in the loop, and viewer agent may not have noticed that `scene.add` could also be folded into the registration path. They also probably did not address the timing issue: `createGridForFileAsync` is called in parallel via `Promise.all`, and Map insertion order depends on which promise resolves first, meaning grid order in the registry is nondeterministic across loads -- unlike the old `push` which happened sequentially after `Promise.all`.
