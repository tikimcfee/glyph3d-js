# Predictions: prior-art-lessons

## rendering-backend-portability

I predict this agent concluded that the thinnest viable GPU abstraction is a contract around instanced draw calls -- something like "submit N instances with these 5 typed arrays, this atlas texture, and these uniforms." They likely mapped the glyph3d-js rendering contract (positions, sizes, glyphIds, colors, groupIds + atlas texture + highlight texture) across WebGL2, WebGPU, wgpu/Vulkan, and Metal, finding that instance attributes, texture sampling, and offscreen render targets (for picking) are universally available on all modern APIs. Their proposed abstraction is probably a thin adapter interface (`createInstancedMesh`, `uploadTexture`, `renderPass`, `readPixel`) rather than a full scene graph, with Three.js and wgpu as the two concrete backends. They likely flagged the picking system's `readPixels` as the trickiest cross-API concern, since async GPU readback differs significantly between WebGL2 (synchronous), WebGPU (async buffer mapping), and Vulkan (fence + map).

## universal-text-pipeline

I predict this agent identified four pipeline stages -- font discovery, text shaping, glyph rasterization, and buffer building -- and concluded that only the last two are truly portable. They likely argued that font discovery and shaping are inherently platform-specific (browser delegates to the OS via Canvas 2D; native needs cosmic-text, HarfBuzz, or platform APIs), while atlas packing (shelf algorithm) and buffer building (text to typed arrays) are pure computation with no platform dependencies. The buffer contract (`GlyphBufferSet` of Float32Arrays) was probably identified as the portability seam -- everything upstream of it can vary by platform, everything downstream is universal. They likely proposed a `FontProvider` or `RasterizerBackend` interface that outputs `{ bitmap, width, height, bearing }` per glyph, noting that glyph3d-js's Canvas 2D `fillText()` already serves this role implicitly for the browser.

## device-tier-scaling

I predict this agent defined 3-4 device tiers (high-end desktop, mid-range laptop/tablet, low-end mobile/integrated GPU, and possibly a "minimal" tier for very old hardware) and proposed scaling knobs around instance count limits, atlas resolution, highlight texture size, and worker pool size. They likely concluded that the primary memory constraint is the atlas texture (2048x2048 RGBA = 16MB) and the instance buffers (40 bytes per glyph, so 10K glyphs = 400KB, 100K glyphs = 4MB), and proposed tiered caps. For degradation, they probably suggested reducing atlas resolution (1024x1024), disabling the picking system on low-end devices (eliminating the offscreen render target), reducing max instances per mesh, and falling back to main-thread buffer building when workers are unavailable. They may have also flagged that frustum culling via GridVirtualizer is the single most impactful optimization for low-end devices, since it eliminates draw calls entirely rather than just reducing per-call cost.

## data-source-abstraction

I predict this agent proposed a provider interface for feeding text content into the rendering pipeline, abstracting over local filesystem, GitHub API, WebSocket relay, and potentially LSP or other structured sources. The contract is probably something like `{ listEntries(path) -> Entry[], readFile(path) -> string, watch?(path) -> stream }` with async iteration. They likely addressed incremental updates -- when a file changes, you need to update only the affected CodeGrid's buffers rather than rebuilding everything -- and proposed an event-based or observable pattern (file changed, file added, file removed) that maps to CodeGrid lifecycle operations. They probably noted that the existing codebase already has multiple ad-hoc data sources (the GitHub viewer fetches from the API, the IDE shell reads from WebSocket relay, the filesystem provider reads locally) and argued for unifying them behind a single interface so that CodeGrid and the layout managers don't need to know where content comes from.
