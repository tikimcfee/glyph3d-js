# Predictions: rendering-backend-portability

## universal-text-pipeline

I predict they identified two clearly separable layers: (1) text shaping and layout (Canvas 2D `fillText`, `measureText`, line wrapping, grapheme clustering) and (2) GPU buffer construction (the `buildBuffers` / `textToGlyphs` / `layoutText` pipeline in `src/workers/builders/`). The worker builders are already platform-agnostic pure functions operating on arrays and codepoints -- they likely called these out as the portable core. The platform-coupled bottleneck is atlas generation: `GlyphAtlas.js` depends on Canvas 2D for rasterization and `measureText` for per-glyph metrics, which maps to CoreText/DirectWrite/FreeType on native platforms. I expect they proposed an interface boundary where the atlas provides a metrics table (glyph widths, UV rects, texture dimensions) and a rasterized bitmap, and everything downstream of that -- buffer building, layout computation, the `Float32Array` assembly -- consumes that contract without caring how the bitmap was produced. They likely flagged grapheme cluster handling (`Intl.Segmenter` or equivalent) as another browser-specific dependency that needs a portable shim.

Confidence: High. My own analysis explicitly identified Canvas 2D atlas generation as "the true portability bottleneck," and the worker/builder architecture is visibly designed for exactly this separation.

## device-tier-scaling

I predict they organized devices into roughly 3-4 tiers: high-end desktop GPU (10K+ instances at 60fps, full feature set), mobile/integrated GPU (2-5K instances, reduced atlas size or lower aniso filtering), and software rasterizer / low-end (1-2K instances at reduced framerate, possibly without picking). They likely identified the 5 vertex texture fetches per instance as the primary scaling bottleneck on lower tiers, since vertex texture bandwidth is the weakest link on mobile GPUs. Memory budgets probably centered on: atlas texture (2048x2048 RGBA8 = 16MB), atlas map texture (RGBA32F, scales with charset), highlight texture (small), and instance buffers (40 bytes/glyph * 10K = 400KB) -- with the atlas being the dominant cost. I expect they proposed `maxInstancesPerMesh` as the primary scaling knob (already exists at 10K), possibly with atlas resolution reduction (1024x1024) and disabling picking on the lowest tier. They may have flagged RGBA32F vertex texture sampling as the one feature that could fail on some older mobile GPUs (even within ES 3.0, the `OES_texture_float_linear` situation), requiring a fallback to per-instance attribute packing. The hard wall is likely the same one I found: ES 3.0 minimum.

Confidence: Medium-high. The scaling knobs are fairly obvious from the architecture. I'm less certain about specific memory budget numbers they would have computed or whether they proposed dynamic tier detection versus configuration-based.

## data-source-abstraction

I predict they analyzed the existing `FileSystemProvider` abstraction (the filesystem provider layer mentioned in MEMORY.md) and the GitHub API path in `GitHubRepoViewer.js`, and proposed a provider contract that returns file content as strings/buffers with metadata (path, language/type, size). They likely identified three source types: local filesystem (Node.js `fs` or browser File System Access API), remote HTTP/API (GitHub, generic REST), and WebSocket relay (the existing `ws-relay` server). For incremental updates, I expect they proposed either a change-event stream (file watcher / WebSocket push) or a poll-and-diff model, where the provider signals which files changed and the pipeline only rebuilds affected CodeGrids. They probably emphasized that the provider must be async (all sources involve I/O) and that the contract should include directory listing/tree traversal (for `HierarchicalLayoutManager`) in addition to file content reads. They may have proposed a `readFile(path) -> Promise<{content, metadata}>` and `listDirectory(path) -> Promise<Entry[]>` minimal interface, with optional `watch(path, callback)` for live updates.

Confidence: Medium. The filesystem provider layer is already a project concept (per MEMORY.md), so they had prior art to analyze. I'm guessing at the specific interface shape, but the async + content/metadata + directory listing pattern is fairly standard.

## prior-art-lessons

I predict they analyzed several projects: **wgpu** (Rust GPU abstraction layer -- relevant because it solves the exact cross-API problem I scoped), **xi-editor** or **Zed** (GPU text rendering in a code editor context, using Metal/Vulkan), **Alacritty** (GPU-accelerated terminal with instanced glyph rendering, very close to glyph3d-js's pattern), possibly **Monaco/VS Code** (as the dominant code editor, though it uses Canvas 2D not GPU instancing), and potentially **mapbox-gl** or **deck.gl** (WebGL instancing at scale for a different domain). Universal patterns they likely identified: atlas-based glyph caching is ubiquitous, instanced rendering is the standard approach for large glyph counts, and the text-shaping/rasterization layer is always platform-specific while the GPU submission layer is always abstractable. They probably recommended: (1) adopt wgpu or a wgpu-like abstraction if going native rather than writing per-API backends from scratch, (2) use SDF (signed distance field) rendering for resolution-independent glyphs (Alacritty and many game engines do this), and (3) keep the current RGBA bitmap atlas approach for now since it matches Canvas 2D output directly but plan an SDF migration path. They may have flagged that glyph3d-js's use of `gl_InstanceID` for derived picking IDs is somewhat unusual -- most GPU text renderers use per-instance color IDs or CPU raycasting instead.

Confidence: Medium. I'm fairly confident about wgpu and Alacritty appearing in the analysis since they're the most directly relevant projects. I'm less certain about which specific recommendations they made -- SDF rendering is an obvious suggestion but might be out of scope for a portability-focused analysis. The specific projects they chose could vary significantly.
