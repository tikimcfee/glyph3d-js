# Predictions: shader-rendering

## shaping-pipeline

I expect the shaping-pipeline agent concluded that HarfBuzz WASM (hb-subset.wasm or harfbuzzjs) is the right integration path, loaded via a Web Worker to avoid blocking the main thread, with the shaped glyph output (glyph IDs, advances, offsets) fed into the existing buffer builders (`buildBuffers.js` / `layoutText.js`) where `charWidth` is replaced by per-glyph advance widths from the shaping result. Their key concern is likely the font loading pipeline -- specifically that `.ttf`/`.otf` binary data must be fetched and passed into the WASM shaper, and that the `GlyphAtlas` must be re-keyed from Unicode codepoints to HarfBuzz glyph IDs, which ripples through `textToGlyphs.js` and `instanceCodepoint` semantics. They likely designed the shaping cache as a map from `(fontId, textRun)` to shaped output, and flagged that Worker communication needs the font binary transferred once (via SharedArrayBuffer or structured clone) rather than per-job, with the atlas UV map sent to workers only after re-indexing by glyph ID.

## migration-integration

I expect the migration-integration agent produced a phased file-change manifest showing Phase A touching approximately 8-12 files (GlyphAtlas, buffer builders, layoutText, textToGlyphs, WorkerBridge message protocol, GlyphCollection, and font loading infrastructure) while Phase B touches fewer files but with deeper changes (GlyphRenderer shaders, new curve/band texture loaders, and picking system adjustments). Their primary risk concern is likely that Phase A is the high-risk phase because it changes the data flow from Unicode codepoints to glyph IDs across the entire pipeline, with breakage in highlighting, picking, and semantic mapping if any file still assumes codepoint-based indexing. For font bundling in the Go binary, they likely proposed embedding a default `.ttf` alongside the existing `//go:embed` assets and serving it via the same HTTP path mechanism. They probably recommended a hybrid/LOD fallback strategy where the bitmap atlas remains available as a fallback for browsers or zoom levels where Slug is too expensive, and flagged that the testing strategy must include visual regression comparison at multiple glyph sizes since the rendering output fundamentally changes from sampled bitmaps to evaluated curves.
