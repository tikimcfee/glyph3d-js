# Predictions: Pipeline

## Predicting Memory Agent (byte counts, retained references, deferred allocation)

I expect Memory concluded that the per-renderer highlight texture is the dominant memory concern at scale. Each `GlyphRendererV15` instance owns its own RGBA8 DataTexture sized to `HIGHLIGHT_TEX_WIDTH` (1024) wide, growing in height with instance count. At 1500 CodeGrids, each with its own `GlyphCollection` -> `GlyphRendererV15`, that is 1500 separate highlight textures. Even at modest sizes (say 500 glyphs per grid = 2KB each), that is ~3MB of highlight data alone, most of it all-zeros since highlights are rare. Memory likely recommended a shared or pooled highlight texture, or lazy allocation (don't create the highlight texture until `setGlyphHighlight` is actually called), or a sparse representation instead of a dense RGBA8 array.

I expect Memory also flagged the deferred `_pendingOps` array in `GlyphCollection` as a retained reference concern. Each `addText()` call pushes an object with the full text string, position, color, and options onto `_pendingOps`. If `flush()` is never called (or is delayed), these accumulate. The text strings themselves are the heavy part -- a 2000-line source file is ~60KB of string data sitting in `_pendingOps` until flush. Memory likely recommended either streaming the text through shaping immediately (producing shaped data that is more compact) or at minimum ensuring `_pendingOps` is nulled after flush rather than just `.length = 0` (which retains the array's internal capacity).

I also expect Memory identified the `_groupTexture` (Float RGBA DataTexture, 4 columns x maxGroups rows) as a per-renderer allocation that could be shared or pooled, since most CodeGrids use only group 0 (default) and never set custom group transforms. The default identity-filled group texture is duplicated 1500 times for no reason. Memory likely recommended either a shared immutable default group texture or lazy creation on first `setGroupTransform` call.

## Predicting GPU Agent (VRAM, draw calls, texture sharing, shader efficiency)

I expect GPU concluded that the three Slug textures (curveTexture, bandTexture, glyphMapTexture) are already correctly shared -- the comment at line 1632 of GlyphRenderer.js explicitly says "Don't dispose Slug textures -- they're shared across all renderers" and they are passed by reference from the atlas. So GPU likely confirmed this is already optimal and focused elsewhere.

I expect GPU's primary concern was the per-renderer material/shader program duplication. Each `GlyphRendererV15` creates its own `THREE.RawShaderMaterial` with identical GLSL source but separate uniform objects. Three.js compiles and links a new WebGL program per material instance unless it detects identical shader source. GPU likely investigated whether Three.js actually deduplicates these (it does via program caching keyed on shader source hash), but even with deduplication, 1500 separate material instances means 1500 separate uniform state objects and 1500 `gl.useProgram` / `gl.uniform*` call sequences per frame for visible grids. GPU likely recommended either a shared material with per-draw uniform updates (using `onBeforeRender` callbacks) or consolidating multiple CodeGrids into fewer, larger renderer instances to reduce draw call overhead.

I expect GPU also analyzed the picking pass cost. The `PickingSystem` does a material-swap second render pass over the entire scene. With frustum culling, only ~10-50 grids are visible, but the picking pass iterates all registered renderers (`_renderers` Map) to swap materials, even for culled grids. GPU likely recommended filtering the picking pass to only visible/frustum-intersecting renderers, and possibly noted that the picking render target auto-resizes to full canvas resolution when a half-resolution target would suffice for single-pixel readback.

GPU likely also flagged the highlight texture as a VRAM concern (overlapping with Memory's analysis but from the GPU side): 1500 separate texture binds per frame is expensive even if the textures are small, and recommended either a texture atlas approach (single large highlight texture shared across grids, indexed by a per-renderer offset uniform) or lazy VRAM allocation (don't upload the texture to the GPU until highlight data is actually written).
