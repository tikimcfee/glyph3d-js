# Predictions: GPU

## Predicting Agent Memory (byte counts, retained references, deferred allocation)

I expect Memory concluded that the dominant JS-heap cost is the instance Float32Arrays -- 6.1M glyphs at 40 bytes each means ~244 MB of typed arrays on the JS side that mirror the GPU buffers. Three.js InstancedBufferAttribute holds a reference to the source array even after upload, so these arrays are retained in JS heap indefinitely. Memory likely flagged this as the single largest retained-reference problem: every CodeGrid keeps its GlyphCollection alive, which keeps its GlyphRendererV15 alive, which keeps five Float32Arrays alive. The entire chain is rooted by the GitHubRepoViewer's grid registry or the GridVirtualizer's registration map.

I expect Memory identified the GlyphAtlas canvas (2048x2048 = 16 MB system RAM) as a secondary concern and likely recommended lazy-disposing it after initial metrics extraction, or at least shrinking it once dynamic glyph addition is no longer expected. They probably also flagged the atlas's `_glyphWidths` and `_uvMap` objects as retained dictionaries that grow monotonically and are never pruned.

I predict Memory's key recommendation was to enable eviction by default (same conclusion I reached) but from a different angle -- they would frame it as breaking the retained-reference chain so the GC can reclaim the ~244 MB of JS-heap Float32Arrays for off-screen grids, not just the GPU-side VRAM. They likely also recommended that `unloadContent()` should explicitly null out the typed array references (not just call `dispose()` on the Three.js objects) to ensure the GC can collect them, since Three.js dispose sometimes leaves dangling `.array` references on InstancedBufferAttribute.

Memory probably also flagged the deferred allocation pattern in GlyphCollection -- `addText()` queues operations and `flush()` allocates buffers. They likely noted that if flush is never called (or called multiple times after incremental additions), there could be intermediate allocations that are immediately discarded. The worker path (`applyPrebuiltBuffers`) bypasses this by swapping in pre-built arrays, which is more efficient but creates a brief window where both old and new arrays exist simultaneously (doubling peak memory during the swap at `GlyphRenderer.js:1433-1444`).

I expect Memory recommended a "budget" system -- tracking total allocated bytes across all grids and triggering eviction when a threshold is crossed, rather than relying solely on frustum distance. They may have also suggested pooling or recycling Float32Arrays across grid load/unload cycles to avoid GC pressure from large allocation churn.

## Predicting Agent Pipeline (dead code, dual paths, builder simplification)

I expect Pipeline concluded that there are two parallel rendering codepaths that should be unified: the "sync" path through `_rebuildAllInstances()` and the "worker" path through `applyPrebuiltBuffers()`. The sync path is a fallback that rebuilds all glyph data on the main thread when workers are unavailable. Pipeline likely identified that maintaining both paths creates code duplication in how buffers are constructed and applied, and recommended either deprecating the sync path or extracting the shared buffer-building logic into a single function that both paths call.

I predict Pipeline found dead or vestigial code in the `src/layout/` directory -- `GlyphLayout.js`, `GlyphBatcher.js`, and `GlyphInstancePool.js` are described as "partially deprecated" in the project structure. Pipeline likely recommended removing them entirely, since the worker builders (`src/workers/builders/buildBuffers.js`, `textToGlyphs.js`, `layoutText.js`) have fully replaced their functionality. They may have also identified that some methods on GlyphCollection (like the older `addText`/`flush` deferred pattern) are now only used by the sync fallback path and could be simplified if the sync path is removed.

I expect Pipeline flagged the group transform system as over-engineered for CodeGrid's actual usage. CodeGrid always uses groupId 0 with an identity transform, so the entire group creation/management/texture machinery (`createGroup`, `setGroupTransform`, the 64-row group DataTexture) is dead weight for the primary use case. Pipeline likely recommended either removing the group system from CodeGrid's path entirely or making it opt-in (lazy-initialize the group texture only when `createGroup()` is first called with a non-zero group).

Pipeline probably also examined the `GlyphCollection` -> `GlyphRendererV15` relationship and concluded that GlyphCollection is largely a thin wrapper that proxies calls to the renderer. They may have recommended collapsing the two classes or at least clarifying their separation of concerns -- GlyphCollection manages text semantics (addText, line tracking, semantic info) while GlyphRendererV15 manages GPU resources. Pipeline would want these boundaries made explicit rather than having the collection reach into renderer internals.

I also expect Pipeline identified the `ShaderManager.js` in `src/core/` as potentially unused or underutilized, since GlyphRendererV15 constructs its shaders inline rather than going through the ShaderManager. They likely recommended either routing shader construction through ShaderManager (which could then cache and share compiled programs -- addressing the 555-material-duplication problem I identified) or removing ShaderManager if nothing uses it.
