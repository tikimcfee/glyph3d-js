# Predictions: Memory

## Pipeline Agent (dead code, dual paths, builder simplification)

I expect Pipeline concluded that the `src/layout/` directory (GlyphBatcher.js, GlyphInstancePool.js) is dead code that should be deleted outright, since both files carry explicit `@deprecated` annotations saying they are safe to remove. Pipeline likely flagged GlyphLayout.js as nearly dead too -- it is only instantiated as a lazy fallback inside `GlyphRendererV15._textToGlyphs()` when no HarfBuzz shaper is available. Since the production path always has a shaper, GlyphLayout becomes dead weight that Pipeline would recommend removing (or gating behind a strict check that errors rather than silently falling back).

Pipeline almost certainly identified the three-way builder duplication as the core simplification target: `buildGlyphBuffers` (single-item legacy), `buildBatchBuffers` (multi-item legacy grapheme path), and `buildShapedBatchBuffers` (HarfBuzz path). The legacy grapheme builders iterate grapheme clusters and look up atlas UV maps; the shaped builder reads pre-shaped HarfBuzz data. Pipeline likely recommended collapsing to a single `buildShapedBatchBuffers` entry point and removing the grapheme fallback entirely, since HarfBuzz shaping is now the only production path. The `codepoints` alias kept alongside `glyphIds` for backward compatibility would be another thing Pipeline flagged for removal -- it is a naming alias on the same Float32Array that serves no purpose except confusion.

I also expect Pipeline identified the dual sync/async rendering paths as a maintenance hazard. GlyphRendererV15 has both `render()`/`renderBatch()` (sync, builds glyph JS objects, calls `_rebuildAllInstances`) and `applyPrebuiltBuffers()` (async worker path, reconstructs glyph objects from typed arrays). The sync path is used only as a fallback (GlyphCollection line 672-693). Pipeline would recommend removing the sync fallback in GlyphCollection entirely and treating worker failure as a hard error, since workers are universally supported. This eliminates the need for the sync-path methods `render()`, `renderBatch()`, `_textToGlyphs()`, `_textToGlyphsShaped()`, `_registerText()`, and `_rebuildAllInstances()` in GlyphRenderer -- roughly 200 lines.

Pipeline's key concern is likely that these dual paths create a false sense of robustness while actually masking bugs: the sync path builds glyph objects differently than the async reconstruction path, and any behavior divergence goes unnoticed until someone hits the fallback.

## GPU Agent (VRAM, draw calls, texture sharing, shader efficiency)

I expect GPU concluded that the Slug textures (curveTexture, bandTexture, glyphMapTexture) are properly shared -- they are created once by SlugEncoder and passed by reference through atlas._slugData to every GlyphRendererV15 instance. GPU would have confirmed this is correct and not a source of VRAM duplication. The three textures together are small (likely under 500 KB for a ~500-glyph charset), so GPU would note this as a non-issue.

GPU's primary VRAM concern is likely the per-renderer duplication of group DataTextures and highlight DataTextures. Each of the 555 renderers creates its own group DataTexture (4 KB each) and highlight DataTexture (sized to glyph count, 4 bytes/glyph). GPU would note that while these must be per-renderer (groups and highlights are per-grid state), the group texture default of 64 groups is wasteful when most grids use only group 0. GPU would recommend the same group texture shrink I identified (start at 4, grow on demand).

GPU almost certainly focused on the fragment shader's winding number computation as the most expensive per-pixel operation. The inner loop processes up to MAX_CURVES_PER_BAND (64) curves per band, with each curve requiring two `texelFetch` calls, coordinate unpacking, and a quadratic bezier intersection test. GPU likely recommended adding fwidth-based anti-aliasing (the comment at line 512 says "Phase 4: fwidth-based AA would go here") and possibly SDF caching or distance field approximation to avoid per-pixel curve evaluation. However, GPU may also have concluded that the band-based early-exit is already effective enough for most glyphs (typical band has 3-8 curves, not 64).

I expect GPU flagged the picking system's second render pass as a VRAM and fill-rate concern. In 'glyph' mode, the picking pass runs the full Slug winding number evaluation a second time -- identical fragment shader cost as the main pass. GPU likely recommended defaulting to 'cell' mode (which is already the default) and noting that 'glyph' mode should only be used when sub-character precision is genuinely needed. GPU may have also recommended halving the picking render target resolution (resolutionScale 0.5) since picking needs pixel-level precision, not sub-pixel.

GPU would identify that frustum culling eliminates draw calls but not VRAM. At 555 grids with ~50 visible, the GPU still holds instance buffers for all 555 grids. GPU's recommendation here would converge with mine: enable eviction to actually free GPU-side buffers for off-screen grids. GPU would frame this as VRAM pressure rather than JS heap (my framing), but the fix is the same.

GPU likely noted that `mesh.frustumCulled = false` (GlyphRenderer.js line 300) disables Three.js's built-in frustum culling for instance meshes, which is correct because GridVirtualizer handles culling at the grid level. But GPU might flag that this means every visible grid's full instance buffer is submitted as a draw call even if most of its glyphs are off-screen within the grid. At 11K glyphs per grid, the vertex shader runs for all 11K even if only 100 are in the viewport. GPU may or may not recommend per-glyph frustum culling (likely not, since the overhead of per-instance CPU-side culling would exceed the vertex shader savings).

Finally, GPU would observe that `transparent: false` and `depthWrite: true` (line 273-275) plus the `discard` in the fragment shader means the GPU cannot benefit from early-Z rejection for empty/space glyphs, since `discard` invalidates the early depth test. GPU might recommend separating space glyphs from rendered glyphs at the buffer level (which the shaped builder already does by skipping empty glyphs), confirming this is already handled correctly.
