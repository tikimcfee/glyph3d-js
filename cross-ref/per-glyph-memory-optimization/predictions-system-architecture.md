# Predictions: system-architecture

## buffer-packing

I expect buffer-packing concluded that the current 14-float (56 bytes) per-glyph layout is the primary optimization target, and proposed reducing it significantly — likely to 8-10 floats — by quantizing positions and sizes to half-floats or 16-bit integers, packing codepoint and groupId into a single uint32, and encoding color as packed RGB565 or RGBA8 instead of 3 separate floats. They likely flagged `instanceAddedColor` (3 floats for highlight overlay) and `instancePickingId` (1 float) as candidates for conditional/sparse storage rather than per-glyph allocation, since most glyphs are never highlighted or picked. Their key concern is probably shader compatibility — quantized attributes need decode logic in the vertex shader, and `InstancedBufferAttribute` type changes interact with WebGL 2's `vertexAttribIPointer` vs `vertexAttribPointer` distinction. I expect they proposed something like 28-32 bytes per glyph as a realistic target, which would halve the GPU memory I calculated at 336 MB down to ~170 MB.

## gpu-techniques

I expect gpu-techniques focused on texture-based instance data (storing per-glyph attributes in a DataTexture sampled in the vertex shader) as the main architectural alternative to buffer attributes, since this unlocks partial updates without re-uploading entire attribute arrays and enables virtual/paged glyph storage. They likely analyzed the atlas itself — the 17 MB DataTexture covering full Unicode range that CLAUDE.md flags as an optimization target — and proposed a sparse or demand-loaded atlas that only allocates pages for codepoints actually used. They probably also examined the picking render pass overhead (the material-swap second pass) and proposed either a compute-shader or stencil-based alternative, or at minimum suggested the picking target resolution can be reduced to 1/4 canvas size without losing accuracy since it only reads a single pixel. Their key concern is likely WebGL 2 limitations (no compute shaders, no SSBO) constraining the texture-based approaches compared to what WebGPU would allow.
