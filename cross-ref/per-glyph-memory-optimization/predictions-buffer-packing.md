# Predictions: buffer-packing

## gpu-techniques

I expect gpu-techniques concluded that the biggest wins come from leveraging WebGL 2 features -- specifically `gl_InstanceID` for derived picking IDs, GLSL ES 3.00 bitwise ops for packed integer attributes, and possibly texture-based indirection (DataTextures or UBOs) for per-group data that is currently duplicated across every glyph. They likely flagged the GLSL version upgrade (ES 1.00 to 3.00 / `THREE.GLSL3`) as the critical gating decision, since `floatBitsToUint`, `gl_InstanceID`, and integer attributes all depend on it. Their key concern is probably shader complexity and the risk of breaking the existing rendering pipeline during migration -- the current shaders use `varying`/`attribute`/`texture2D` which all change syntax under GLSL3. They may also have explored whether the atlas map DataTexture (17 MB, noted in CLAUDE.md) could be restructured as part of this effort, and whether instanced rendering could use interleaved buffer layouts for better GPU cache coherence rather than the current separate-attribute approach.

## system-architecture

I expect system-architecture concluded that the optimization touches nearly every layer of the pipeline -- builders, worker transfer, GlyphRenderer attribute setup, PickingSystem registration, CodeGrid highlight paths, and the shader material -- making a phased migration essential. Their main concern is likely the dual code paths: the sync rebuild path (`_rebuildAllInstances` / `_updateInstanceMesh`) and the async worker path (`buildBatchBuffers` / `applyPrebuiltBuffers`) must stay in lockstep, and any attribute layout change risks divergence. They probably emphasized that `instanceAddedColor` removal is the highest-impact but highest-risk change because it threads through `setGlyphHighlight`, `highlightRange`, and the highlight command handlers, requiring a replacement mechanism (likely a highlight DataTexture or re-routing through the group color-blend system). They likely recommended a migration strategy that preserves the existing public API surface (`addText`, `flush`, `highlightRange`, `setGlyphHighlight`) while changing the internal buffer layout, and flagged the JS-side shadow copies in `renderedTexts` as a separate but related memory concern worth addressing.
