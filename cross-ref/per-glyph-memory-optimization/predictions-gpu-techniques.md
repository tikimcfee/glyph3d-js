# Predictions: gpu-techniques

## buffer-packing

I expect buffer-packing concluded that the 14-float (56-byte) per-glyph layout has significant waste from alignment and redundant precision, and proposed packing multiple values into fewer floats using bit-packing or mixed-type typed arrays (e.g., Uint8 for color channels, Uint16 for grid coordinates, interleaved buffer layouts). Their key concern is likely the tension between packing density and WebGL/Three.js attribute alignment requirements — `InstancedBufferAttribute` wants typed arrays of uniform element size, and interleaving heterogeneous types into a single buffer requires careful stride/offset management that Three.js does not natively expose well. I expect they proposed reducing per-glyph cost to somewhere in the 24-32 byte range by converting `instanceColor` from 3 floats to 3 or 4 packed bytes (Uint8, normalized), shrinking `instanceSize` to a shared value or smaller type, and possibly merging `instanceCodepoint` and `instanceGroupId` into a single packed uint32 — but flagged that partial buffer updates become harder with interleaved layouts and that the worker builders (`buildBuffers.js`) would need significant rework to emit packed formats.

## system-architecture

I expect system-architecture concluded that per-glyph memory optimization cannot be evaluated in isolation from the broader allocation and update lifecycle — specifically the `GlyphRenderer._rebuildAllInstances()` full-rebuild pattern, the `renderedTexts` map's sparse slot management, and the `GlyphCollection` deferred flush model. Their main concern is likely that reducing per-glyph byte cost is only half the story; the other half is eliminating redundant full-buffer re-uploads when only a few glyphs change (the current `needsUpdate = true` flags cause Three.js to re-upload entire typed arrays). I expect they proposed a tiered architecture: immutable layout data (position, codepoint, size) set once at flush time and never re-uploaded, versus mutable presentation data (color, highlight) in a separate buffer or texture that supports partial updates. They likely also raised the question of whether `CodeGrid` should own its own `GlyphRenderer` instance (current design) versus sharing a renderer pool, and flagged that the 10,000-instance cap per mesh means the system already splits into multiple draw calls for large files — a concern that interacts with any picking ID or buffer packing scheme that assumes contiguous allocation within a single mesh.
