# Predictions from migration-path agent

## 1. ownership-boundaries agent (dependency-graph + component-ownership)

I expect the ownership-boundaries agent identified approximately 3-4 files as purely IDE-only: `IDEShell.js`, `ide.html`, `ide.css`, and possibly `ShortcutManager.js` (if it is tightly coupled to IDEShell's keyboard bindings rather than being a general utility). They likely categorized `components/AppShell.js` and `components/CommandBar.js` as shared or viewer-owned, since those predate the IDE layout. The bulk of files -- `GitHubRepoViewer.js`, `SceneContext.js`, `SelectionManager.js`, `FileStateManager.js`, all of `websocket/`, and all builders -- would have been flagged as viewer-owned or shared.

Their key coupling concern was almost certainly the 4 import statements in `IDEShell.js` that reach into `components/Drawer.js`, `components/LogCapturePanel.js`, `components/DiffPanel.js`, and `platform.js`. These are the same cross-boundary edges I found. They may have also flagged `components/MinimapOverlay.js` and `components/TouchController.js` as ambiguous -- used by the IDE layout's editor area but defined as viewer components. I expect them to recommend that `IDEShell.js` continues to import from `github-viewer/` rather than duplicating or extracting a shared layer, since the dependency direction (IDE depends on viewer, never the reverse) is clean and one-directional.

They likely expressed concern that `StatePersistence.js` straddles both worlds (it persists IDE layout state like sidebar width alongside viewer state like last-opened repo), and may have flagged it as a file that needs attention during separation but not necessarily movement.

## 2. server-socket agent

I expect the server-socket agent concluded that the WebSocket relay (`ws-relay.mjs` / `ws-relay.py`) should stay in `examples/github-viewer/` for now, or alternatively be promoted to a top-level `examples/shared/` or project-root location. Their reasoning would be that the relay is fully location-agnostic -- it binds to a configurable host/port with no hardcoded filesystem paths, no references to `github-viewer` or `ide` in its routing logic, and no dependency on either example's HTML or JS. The `WebSocketBridge.js` client connects to `ws://localhost:8765` by default, which is independent of where the relay script lives on disk.

They likely recommended that the relay remain in `github-viewer/` as the simpler option (avoiding churn), but noted that if the IDE example wants its own standalone launch script (`npm run ide` or similar), the relay invocation path in `package.json` would need updating or a second script added. Their main concern would be the `websocket/` directory's `CommandRouter.js` and TUI subsystem, which is more tightly coupled to the viewer's `ViewerAPI.js` -- they likely flagged that the TUI/command layer is viewer-specific even though the transport layer (relay + bridge) is generic. They may have suggested that `WebSocketBridge.js` could eventually move to a shared location, while `CommandRouter.js`, `ViewerAPI.js`, and the TUI files stay with the viewer.
