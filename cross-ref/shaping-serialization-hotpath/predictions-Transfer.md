# Predictions: Transfer Agent

**About Shaping Agent:** They likely dissected the `HarfBuzzShaper.shape()` method and discovered that `buffer.json()` internally calls `serialize("JSON")` then `JSON.parse()`, creating a WASM-to-string-to-objects round-trip that costs roughly as much as the `hb_shape()` WASM call itself. Their key finding is probably that harfbuzzjs exposes `getGlyphInfosAndPositions()` for direct HEAP32 reads, bypassing the serialize/parse pipeline entirely. They probably also proposed moving shaping off the main thread into a small number of dedicated workers (2-3) with their own WASM instances, capped to avoid the OOM that killed the original per-worker-HarfBuzz design.

**About Caching Agent:** They probably recognized that for a monospace font like Cousine-Regular, HarfBuzz shaping is pure overhead after the first encounter of each codepoint -- every character maps 1:1 to a fixed glyph ID with a uniform advance width. Their proposal is likely a per-codepoint lookup table (perhaps ~256 entries, a few KB) primed during font init that replaces all runtime WASM calls with simple map lookups. They may have also noted that `buildBatchBuffers` only reads `sg.g` and `sg.ax` from the shaped output, meaning `cl`, `ay`, `dx`, `dy`, and `flags` are dead fields that inflate both memory and transfer cost for no purpose.
