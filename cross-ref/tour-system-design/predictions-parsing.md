# Predictions: parsing

## Rendering Agent
I expect the rendering agent concluded that the tour system's visual layer should build on the existing `CodeGrid`-as-annotation pattern (already present in `createTourAnnotation`) and the `highlightRange` API for marking referenced code regions, proposing a `TourOverlay` or similar component that manages annotation grids, highlight state, and possibly connecting visual elements (lines/arrows between source and target). Their key concern would be lifecycle management of ephemeral visual elements -- ensuring highlight texels and annotation CodeGrids are created/cleared in lockstep with tour stop transitions, and that the highlight DataTexture doesn't accumulate stale state across stops. They likely designed around the constraint that highlights are additive RGBA8 texels written via `setGlyphHighlight`, meaning they need explicit clear-on-transition logic, and proposed that visual state be driven declaratively from parsed `FileRef` data (my output) rather than imperatively, so the renderer can batch-clear and batch-apply per stop.

## Orchestration Agent
I expect the orchestration agent concluded that tour playback should be modeled as a state machine (idle/playing/paused/transitioning) layered on top of the existing `tour.*` command handlers in `navigationCommands.js`, with the core addition being a `TourRunner` or `TourController` class that owns the play loop, stop sequencing, and cancellation -- replacing the current inline `for` loop + `await setTimeout` approach. Their key concern would be the integration seam: how parsed references (my `ParseResult`) get resolved to grid indices and line ranges at runtime, since grids may load asynchronously or be virtualizer-culled. They likely proposed a resolver step that suffix-matches `FileRef.filePath` against `grid.userData.sourcePath` (the same pattern `findGrid` uses in `highlightCommands.js`), converts my 1-based line/col to 0-based, and feeds concrete `{ gridIndex, startLine, startCol, endLine, endCol }` tuples to the rendering layer. They would also have addressed tour definition persistence (extending the current in-memory `Map<string, TourDefinition>` to support serialization) and the coordination protocol between parsing, resolution, and playback phases.
