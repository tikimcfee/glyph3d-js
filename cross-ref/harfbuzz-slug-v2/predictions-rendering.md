# Predictions: rendering

## plumbing
They likely concluded that harfbuzz-wasm should be vendored as a pre-built WASM binary (not compiled from source), loaded via `WebAssembly.instantiateStreaming` in a shared initialization path, and that the WASM module must be transferable to Web Workers since the buffer builders run there. The font file (a single .ttf/.otf for the code font) gets fetched once, its ArrayBuffer shared to workers via structured clone or SharedArrayBuffer, and HarfBuzz's `hb_shape()` returns glyph IDs plus advance widths that replace the current per-codepoint fixed-width assumption. They probably flagged that the Go embed system needs to include the WASM blob alongside the font file, and that WorkerBridge's round-robin dispatch needs the WASM module pre-initialized in each worker before any shaping calls.

## encoding
They likely concluded that SlugEncoder is a pure-function module (no DOM, worker-compatible) that takes HarfBuzz-shaped glyph IDs plus the font's curve data and produces three packed DataTextures: curveTexture (RGBA16UI, one texel per quadratic Bezier with control points normalized to glyph bounding box), bandTexture (RG16UI, horizontal band-to-curve-range mapping), and glyphMapTexture (RGBA16UI, glyph ID to curve/band offset indirection). They probably emphasized that band count per glyph should be tunable (defaulting to 8 horizontal bands), that curves within each band must be sorted by max-y for the early-exit optimization the fragment shader relies on, and that the encoder caches per-glyph results so repeated codepoints (common in source code) only get encoded once. Total texture memory for a code font charset would be roughly 30-80KB versus the current 16MB atlas bitmap.
