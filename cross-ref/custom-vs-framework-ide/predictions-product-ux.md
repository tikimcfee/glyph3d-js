# Predictions from Product/UX Agent

## Engineering Agent Prediction

I expect the engineering agent concluded **keep the custom shell**, primarily because the integration surface between a VSCode/Theia framework and a WebGL canvas "editor area" is fundamentally adversarial. Their analysis likely focused on the fact that frameworks like Theia assume Monaco occupies the editor region and expose extension APIs (ExtensionHost RPC, webview iframes, tree view providers) that have no meaningful mapping to Three.js scene graph manipulation -- so the integration cost is not "high" but structurally unbounded. They probably flagged the input/keybinding conflict as a critical architecture concern: Three.js camera controls, CommandBar focus gating, and a framework's keybinding service would create a three-way event routing nightmare that would generate ongoing maintenance bugs rather than a one-time integration cost. I expect they also noted the LOC comparison favors custom (~2,600 lines of straightforward DOM code vs. pulling in megabytes of framework with its own build pipeline, bundler requirements, and module resolution assumptions that conflict with the project's zero-build-step ES Modules architecture). Their key concern is likely that adopting a framework would force introducing a build system (webpack/esbuild) for the first time, which is a foundational change to the project's development model.

## Sustainability Agent Prediction

I expect the sustainability agent concluded **keep the custom shell**, but with more nuance and possibly some hedging about long-term solo-dev risk. Their analysis likely centered on three concerns: (1) Theia/Code OSS are governed by large organizations (Eclipse Foundation, Microsoft) whose roadmaps are not aligned with a niche 3D text rendering tool, meaning upstream breaking changes would impose unplanned maintenance on a solo developer with no leverage over the release schedule; (2) the MIT/Eclipse license terms are permissive but forking to shim a WebGL canvas into the editor area would create a de facto hard fork that drifts from upstream quickly, making the "community support" benefit illusory; and (3) the current ~2,600-line custom shell is within solo-dev maintenance capacity precisely because it has no external dependency beyond Three.js, whereas a framework dependency would multiply the surface area of things that can break without any action by the maintainer. They likely flagged that the only sustainability argument *for* a framework would be if the project needed to attract contributors who expect familiar VSCode extension patterns, but concluded this is unlikely given the product's novel spatial paradigm. Their key concern is probably that solo-dev viability depends on keeping the dependency graph shallow, and a framework integration would be the single largest risk to long-term maintainability.
