# Predictions from Event Pipeline Agent

## Predicting: Spatial Mechanics Agent

I expect the Spatial Mechanics agent concluded that screen-to-world projection for drag should reuse the exact FOV-based math already present in ViewerCameraController._applyDragTranslation, because that function already solves the pixel-delta-to-world-delta conversion at a given Z depth. My Phase 0 analysis independently derived this same formula for HitDispatcher._screenToWorldDelta, so the Spatial Mechanics agent almost certainly identified it as the canonical approach and recommended extracting it into a shared utility rather than duplicating it across VCC and HitDispatcher. The key concern they likely raised is that the projection math assumes a perspective camera looking down -Z with no rotation -- if pitch/yaw are ever non-zero (VCC only sets them programmatically via focus methods), the simple `tan(fov/2) * distance / canvasHeight` formula breaks, and they probably flagged this as a future-proofing risk that doesn't need solving now but should be documented.

For group layout geometry, I expect the agent analyzed the existing StackLayoutManager (stack/fan/pull-to-workspace) and GridLayoutManager (row/column/plane) and concluded that a WindowGroup should NOT be a new layout manager class, but rather a lightweight container that delegates to one of three modes: "stack" (overlapping Z-offset, reusing StackLayoutManager's stackZOffset/peekY pattern), "splay" (fan-out with X stagger, directly analogous to StackLayoutManager.fanOut), and "free" (no constraints, user-positioned). They likely recommended that the group stores a list of member grid IDs plus a mode enum, and that position updates flow through a single `reflow()` method that applies the appropriate arrangement relative to the group's anchor point. The depth management concern they probably raised is that SelectionManager already uses a Z_POP_AMOUNT of 3 units for selected grids, so window groups need to respect that Z budget -- stacked windows within a group should use smaller Z increments (maybe 0.5-1 unit) to avoid Z-fighting while staying within the selection Z-pop envelope.

For animation, I expect the agent concluded that position interpolation should use a simple lerp driven by the existing requestAnimationFrame loop rather than introducing a tween library. They likely proposed adding an `animateTo(targetPosition, duration)` method on CodeGrid or on a shared AnimationMixin, integrated into the main animate() tick. The concern here would be coordinating animation with drag -- if the user grabs a grid mid-animation, the animation must cancel immediately and yield to direct manipulation.

## Predicting: Integration Surface Agent

I expect the Integration Surface agent concluded that SceneRegistry already has the type system needed for groups -- they would register window groups as a new type (e.g., `'group'`) alongside the existing types ('grid', 'window', 'annotation', 'label', 'agent', 'tour-annotation'). The group entry's `meta` field would store the member grid IDs and the layout mode. Their key insight was probably that SceneRegistry._onChange fires on every mutation, so a WindowGroupManager can subscribe to registry changes and automatically update group membership when grids are unregistered (removed from the scene). This is cleaner than the CustomEvent-based `window-group-request` approach I proposed in my Phase 0, and they likely flagged the tension between my event-driven grouping trigger and a registry-driven membership model.

For SelectionManager interaction, I expect they concluded that selecting any grid within a group should either (a) select the entire group (all members get the `selected` FileStateManager property) or (b) select just the individual grid but bring the whole group's Z-pop forward. They likely chose option (b) because SelectionManager is keyed by sourcePath and changing it to be group-aware would be invasive. The Z-pop concern is real: if you select one grid in a group, the Z_POP_AMOUNT of 3 moves it but not its groupmates, visually breaking the stack. They probably proposed that HitDispatcher (or the group manager) listens to SelectionManager's `on()` callback and applies Z-pop to all group members when any member is selected.

For CodeColorManager group tint, I expect they concluded that a group-level color layer is straightforward -- register a new layer (e.g., `'group-tint'`, priority between selection and heatmap) whose `colorFn` checks whether a file belongs to a group and returns the group's accent color. The `watchProperties` for this layer would include a new `'groupId'` property written to FileStateManager when grids join/leave groups. This fits the existing layered color resolution model perfectly and requires zero changes to CodeColorManager itself.

For the command surface, I expect they proposed commands like `window.group`, `window.ungroup`, `window.group.mode <stack|splay|free>`, and `window.group.list`, following the existing dot-delimited command naming convention visible in the tour and highlight command handlers. The lifecycle concern they likely raised is disposal: when a group is dissolved (ungroup command or last member removed), the group entry must be unregistered from SceneRegistry, group tint must be cleared from all former members via FileStateManager, and Z positions must be restored. They probably flagged that this cleanup chain is the riskiest part of the integration because it touches three systems (registry, color manager, selection manager) and any missed step leaves ghost state.
